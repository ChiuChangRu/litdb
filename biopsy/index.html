🆕 v3.4 更新內容（2026-06-21）
📚 文獻篩選大改版
原本「文庫」頁的「更多篩選」下拉已移除，改搬到「開發策略與資料篩選」頁（原「路線」頁）頂部，分成 8 大分類：類型、擊發機構、鎖合/釋放方式、動作模式、採樣規格訴求、可視化技術、應用部位、廠商。每個分類可獨立切換 OR（任一符合）/ AND（須同時符合），分類之間固定 AND（交集）。旁邊會即時顯示「符合 X / 總篇數」。
✅ 篩選 → 確認 → AI 分析 三步驟流程
在「開發策略與資料篩選」頁勾好篩選條件後，按「📚 進入文庫確認篩選結果，再進行 AI 分析」按鈕，會帶你到文庫頁並彈出確認提示條；確認文獻清單無誤後按「✅ 確認，進行 AI 分析」才會真正生成報告，避免跳過確認直接生成。若中途離開這個流程去其他頁面，篩選條件會自動重置，避免殘留造成混亂。
☁ 雲端同步
新增文獻、AI 深度解析完成、或填寫被引用次數後，文庫頁會顯示「☁ 同步 X 篇待上傳文獻」按鈕，點擊可批次寫回 GitHub 的 papers.json（透過 Worker 代理，不需手動匯出 JSON 檔請人工貼上）。「報告」頁也新增「☁ 儲存到雲端」與「📚 歷史報告」，AI 報告可永久保存、下次免費查看不必重新呼叫 API。
🔗 被引用次數（手動標註）
文獻詳情頁可手動輸入被引用次數並自動記錄查證日期。因 Google Patents 無公開 API、自動化爬取涉及 robots.txt 合規問題，此欄位設計為人工查證後填入，不會自動抓取或即時更新。
🤖 AI 報告品質強化
修正「AI 深度解讀」報告主題偏離問題：原本篩選範圍會把程式內部代號（如 perf）直接送給 AI，AI 看不懂導致報告跑題；現已轉換成中文名稱（性能訴求等），並明確要求三節內容都要緊扣篩選主題本身，AI 也會主動指出哪些文獻雖被篩選命中、但內容其實沒有真正深入主題。
🌳 專利樹分頁位置調整
分頁順序調整為：市場 → 開發策略與資料篩選 → 專利樹 → 文庫 → 報告 → 使用說明。「專利樹」往前移到「開發策略與資料篩選」之後、「文庫」之前。
🛠 其他修正
修正 Console 中無謂的 404/400 請求（PubChem 化學結構圖 image_size 參數錯誤、本地圖片目錄目前無圖檔造成的必然失敗請求）；修正「更多篩選」標籤點擊後沒有視覺反饋的 CSS 範圍限定問題。
📘 AI Agent 文獻閱讀使用說明書
全文實施例拆解 + Claim Coverage 分類
這份 memo 是 LitDB 的 AI 閱讀規格。之後換成不同案件時，請先讓 AI 依照此規格閱讀專利與文獻，再回寫資料庫。
1. 先讀全文
不要只看 abstract、metadata 或 patent title。專利要優先讀 Google Patents / PDF 的 examples、claims、description。
2. 拆實施例
把 numbered examples、embodiments、comparative examples、test tables 分開，不要濃縮成一筆。
3. 分辨資料型態
有實施例看「怎麼做」；沒有實施例但 claim 很寬，看「涵蓋什麼、要避開什麼」。
4. 不硬套
若是材料、結構、包裝、設備或低相關專利，要標註重新分類或低相關，不能硬寫成 coating recipe。
🧭 判讀流程
  1. 確認文獻類型：專利、論文、綜述、市場報告、商用品、設備或測試方法。
  2. 若是專利，先找 Examples / Embodiments / Comparative Examples / Tables / Claims。
  3. 若只有 1 個實施例，通常視為疑慮，需回查全文；但中華民國或中國專利可先保守排除。
  4. 若沒有實施例但 claims 或 description 有明確機構範圍，標為 claim-derived embodiment。
  5. 若全文內容與資料庫標題不符，標示 reclassification_needed，避免誤導報告。
  6. 最後輸出固定欄位，讓前台可一致呈現，不為單篇文獻寫特殊版型。
🧪 每個實施例必填欄位
gauge_length
規格與長度，例如 18G x 15cm、14G x 9cm。
firing_spec.mechanism
擊發機構：雙動作（手動）、SLC彈簧加載、馬達驅動、VABB真空輔助；若無則寫 None。
firing_spec.lock_type
鎖合方式：pawl卡榫式、cam rail解鎖式、雙鎖定卡合；若無則寫 None。
firing_spec.action_mode
動作模式：單動作、雙動作、soft fire漸進式。
results
sample_notch（採樣凹槽）、firing_force（擊發力道）、visibility（可視化技術）、durability、table data。
credibility_reason
說明資料來自全文、表格、claim，或是推論；不要讓推論看起來像事實。
🏷 可信度與標記規則
標記意思使用時機
is_real: true真實實施例全文有 numbered example、comparative example、test table 或明確實驗流程。
is_real: false推論或 claim-derived沒有實驗，但 claim/description 提供明確機構架構或規格範圍。
*推論較少摘要、claim 或 description 很明確，但缺少完整實驗數據。
**推論較多由 claim coverage 或技術脈絡推導，不可當作已實作機構。
reclassification_needed需重新分類全文顯示不是原本標題所說的活檢針機構或不是本案核心。
